# Step 5: Create Kafka Consumer in Notifications Service - Detailed Summary

## Overview
Implemented a complete Kafka consumer infrastructure in notifications-service to consume notification events from multiple Kafka topics. This transforms the service from a REST API to an event-driven consumer with "at least once" delivery guarantees.

## Files Created

### 1. NotificationEvent.java
**Location**: `notifications-service/src/main/java/.../kafka/NotificationEvent.java`

**Purpose**: Data Transfer Object (DTO) for Kafka messages

**Key Fields**:
- `eventId` (String): Unique identifier for idempotency checking
  - Prevents duplicate processing of the same event
  - Format: UUID generated by producer
  - Can be used to check if event was already processed

- `userId` (Long): Target user for the notification
  - Required field
  - Maps to notifications_log.user_id

- `notificationType` (Enum): Type of notification
  - Uses existing Notification.NotificationType enum
  - Determines default title/message if not provided

- `title` (String): Notification title
  - Optional - defaults generated if null
  - Max 200 characters

- `message` (String): Notification message body
  - Optional - defaults generated if null
  - TEXT field in database

- `sourceService` (String): Origin service for tracking
  - E.g., "accounts-service", "cash-service"
  - Useful for debugging and audit trails

- `timestamp` (Long): Event creation time (epoch millis)
  - When the event was generated
  - Not when it was consumed

- `metadata` (String): Additional data as JSON
  - Optional extensibility field
  - Can store extra context (e.g., transaction ID, account number)

**Design Decisions**:

1. **Implements Serializable**:
   - Required for Kafka serialization
   - Includes serialVersionUID for versioning

2. **Uses Lombok**:
   - @Data: Getters, setters, toString, equals, hashCode
   - @Builder: Fluent API for creating events
   - @NoArgsConstructor, @AllArgsConstructor: Required by Jackson

3. **Loose coupling**:
   - No dependency on producer service code
   - Self-contained event structure
   - Forwards/backwards compatible (new fields ignored by old consumers)

4. **Flexibility**:
   - Title/message are optional (defaults provided)
   - Metadata allows extension without schema changes

### 2. KafkaNotificationConsumer.java
**Location**: `notifications-service/src/main/java/.../kafka/KafkaNotificationConsumer.java`

**Purpose**: Kafka message consumer with @KafkaListener

**Key Components**:

#### @KafkaListener Configuration
```java
@KafkaListener(
    topics = {
        "account-created",
        "account-updated",
        "deposit-completed",
        "withdrawal-completed",
        "transfer-initiated",
        "transfer-completed",
        "transfer-failed",
        "notification-event"
    },
    groupId = "${spring.kafka.consumer.group-id}",
    containerFactory = "kafkaListenerContainerFactory"
)
```

**Topic Subscription**:
- Subscribes to 8 topics simultaneously
- Single consumer method handles all topics
- Topic name passed as header for differentiation
- Alternative: Separate @KafkaListener per topic (more code, more control)

**Group ID**: `notifications-service-group`
- All instances of notifications-service share this group
- Kafka distributes partitions among group members
- Enables horizontal scaling

**Container Factory**: Custom factory with manual acknowledgment

#### Method Signature
```java
public void consumeNotificationEvent(
    @Payload NotificationEvent event,
    @Header(KafkaHeaders.RECEIVED_TOPIC) String topic,
    @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,
    @Header(KafkaHeaders.OFFSET) long offset,
    Acknowledgment acknowledgment)
```

**Parameters**:
- `@Payload event`: Deserialized Kafka message
- `topic`: Which topic the message came from
- `partition`: Partition number (for logging/debugging)
- `offset`: Message offset within partition (for tracking)
- `acknowledgment`: Manual ack for "at least once" delivery

#### Processing Logic

**Step 1: Logging**
```java
log.info("Received notification event from topic '{}' [partition={}, offset={}]: eventId={}, userId={}, type={}",
    topic, partition, offset, event.getEventId(), event.getUserId(), event.getNotificationType());
```
- Detailed logging for debugging
- Includes topic, partition, offset for traceability
- Event details for business context

**Step 2: Validation**
```java
if (event.getUserId() == null) {
    log.error("Invalid event: userId is null. EventId={}", event.getEventId());
    acknowledgment.acknowledge(); // Acknowledge to prevent reprocessing
    return;
}
```

**Validation Strategy**:
- Check required fields (userId, notificationType)
- Log errors with eventId for tracking
- **Acknowledge invalid messages** to prevent infinite reprocessing
- Invalid messages are "poison messages" - discard them

**Alternative**: Send invalid messages to Dead Letter Queue (DLQ) for manual review

**Step 3: Idempotency Check** (placeholder)
```java
// Check for idempotency using eventId
// In a production system, you would check if this eventId was already processed
```

**Production Implementation**:
```java
if (notificationRepository.existsByEventId(event.getEventId())) {
    log.warn("Duplicate event detected: eventId={}", event.getEventId());
    acknowledgment.acknowledge();
    return;
}
```

**Why needed**:
- Kafka guarantees "at least once" delivery
- Same message might be delivered multiple times
- Without idempotency check, duplicate notifications created
- eventId ensures exactly-once processing semantics

**Step 4: Convert Event to DTO**
```java
CreateNotificationDTO notificationDTO = CreateNotificationDTO.builder()
    .userId(event.getUserId())
    .notificationType(event.getNotificationType())
    .title(event.getTitle() != null ? event.getTitle() : getDefaultTitle(event.getNotificationType()))
    .message(event.getMessage() != null ? event.getMessage() : getDefaultMessage(event.getNotificationType()))
    .build();
```

**Design**:
- Reuses existing CreateNotificationDTO
- Provides default title/message if not in event
- Decouples Kafka event from business logic

**Step 5: Persist Notification**
```java
notificationService.createNotification(notificationDTO);
```
- Delegates to existing NotificationService
- Service handles database transaction
- If this fails, exception thrown → no acknowledgment → message redelivered

**Step 6: Manual Acknowledgment**
```java
acknowledgment.acknowledge();
```

**Critical for "At Least Once"**:
- Only called after successful database write
- If any exception before this point → no ack → redelivery
- Kafka offset only updated after ack
- Consumer picks up where it left off after restart

**Step 7: Error Handling**
```java
catch (Exception e) {
    log.error("Error processing notification event from topic '{}': eventId={}, error={}",
        topic, event.getEventId(), e.getMessage(), e);
    // Don't acknowledge - message will be redelivered
    throw e;
}
```

**Retry Behavior**:
- Don't acknowledge on error
- Message stays in Kafka
- Consumer retries after error handler delay
- Prevents data loss

**Production Enhancements**:
1. Exponential backoff between retries
2. Maximum retry count
3. After N retries, send to Dead Letter Queue
4. Alert monitoring system

#### Default Title/Message Methods
```java
private String getDefaultTitle(Notification.NotificationType type) {
    return switch (type) {
        case ACCOUNT_CREATED -> "Welcome to MyBank!";
        case DEPOSIT_SUCCESS -> "Deposit Successful";
        // ... etc
    };
}
```

**Purpose**:
- Fallback if producer doesn't provide title/message
- Consistent user experience
- Reduces producer burden (can send minimal events)

**Benefit**: Producers can send:
```json
{
  "eventId": "uuid",
  "userId": 123,
  "notificationType": "DEPOSIT_SUCCESS"
}
```
And consumer generates appropriate title/message.

### 3. KafkaConsumerConfig.java
**Location**: `notifications-service/src/main/java/.../config/KafkaConsumerConfig.java`

**Purpose**: Spring Kafka consumer configuration

#### @EnableKafka
```java
@EnableKafka
public class KafkaConsumerConfig {
```
- Enables Kafka listener detection
- Scans for @KafkaListener annotations
- Configures Kafka infrastructure beans

#### Consumer Factory
```java
@Bean
public ConsumerFactory<String, NotificationEvent> consumerFactory() {
```

**Configuration Map**:

**1. Broker Configuration**
```java
config.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, bootstrapServers);
config.put(ConsumerConfig.GROUP_ID_CONFIG, groupId);
```
- Where to find Kafka brokers
- Which consumer group to join

**2. Deserialization**
```java
config.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
config.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, ErrorHandlingDeserializer.class);
config.put(ErrorHandlingDeserializer.VALUE_DESERIALIZER_CLASS, JsonDeserializer.class.getName());
```

**Why ErrorHandlingDeserializer**:
- Wraps JsonDeserializer
- Catches deserialization errors gracefully
- Prevents consumer from stopping on bad message
- Logs error and continues with next message

**JSON Configuration**:
```java
config.put(JsonDeserializer.VALUE_DEFAULT_TYPE, NotificationEvent.class.getName());
config.put(JsonDeserializer.TRUSTED_PACKAGES, "*");
config.put(JsonDeserializer.USE_TYPE_INFO_HEADERS, false);
```
- TARGET_TYPE: What class to deserialize into
- TRUSTED_PACKAGES: Security - allows deserialization from any package
- USE_TYPE_INFO_HEADERS: Don't require type headers in messages

**3. "At Least Once" Configuration**
```java
config.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);
config.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");
```

**ENABLE_AUTO_COMMIT=false**:
- Disables automatic offset commits
- Offset only committed when we call `acknowledgment.acknowledge()`
- Ensures message processed before offset moves forward
- **Key to "at least once" guarantee**

**AUTO_OFFSET_RESET=earliest**:
- If no offset exists, start from beginning of topic
- Alternative: "latest" (skip existing messages)
- "earliest" ensures no messages missed on first startup

**4. Performance Tuning**
```java
config.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, 100);
config.put(ConsumerConfig.MAX_POLL_INTERVAL_MS_CONFIG, 300000); // 5 min
config.put(ConsumerConfig.SESSION_TIMEOUT_MS_CONFIG, 30000); // 30 sec
config.put(ConsumerConfig.HEARTBEAT_INTERVAL_MS_CONFIG, 10000); // 10 sec
```

**MAX_POLL_RECORDS**: Batch size
- Fetch up to 100 records per poll
- Larger = more throughput, more memory
- Smaller = lower latency, less memory

**MAX_POLL_INTERVAL_MS**: Processing time limit
- Must process batch and call poll() within 5 minutes
- If exceeded, consumer considered dead
- Group rebalances and partitions reassigned

**SESSION_TIMEOUT_MS**: Heartbeat timeout
- If no heartbeat for 30 seconds, consumer dead
- Must be < MAX_POLL_INTERVAL_MS

**HEARTBEAT_INTERVAL_MS**: Heartbeat frequency
- Send heartbeat every 10 seconds
- Keeps consumer alive during processing
- Should be 1/3 of SESSION_TIMEOUT_MS

**5. Fetch Configuration**
```java
config.put(ConsumerConfig.FETCH_MIN_BYTES_CONFIG, 1);
config.put(ConsumerConfig.FETCH_MAX_WAIT_MS_CONFIG, 500);
```

**FETCH_MIN_BYTES**: Minimum data before returning
- 1 = return immediately if any data
- Higher value = wait for more data (batching)

**FETCH_MAX_WAIT_MS**: Maximum wait time
- Don't wait more than 500ms even if FETCH_MIN_BYTES not reached
- Balances latency vs throughput

#### Listener Container Factory
```java
@Bean
public ConcurrentKafkaListenerContainerFactory<String, NotificationEvent> 
    kafkaListenerContainerFactory() {
```

**Purpose**: Creates containers for @KafkaListener methods

**Concurrency Configuration**:
```java
factory.setConcurrency(3);
```
- 3 consumer threads per @KafkaListener
- Each thread consumes from different partitions
- Enables parallel processing
- Must have ≥3 partitions per topic to be effective

**Acknowledgment Mode**:
```java
factory.getContainerProperties().setAckMode(ContainerProperties.AckMode.MANUAL);
```

**AckMode Options**:
- **MANUAL**: Call `acknowledgment.acknowledge()` explicitly (our choice)
- **MANUAL_IMMEDIATE**: Acknowledge immediately after listener returns
- **RECORD**: Acknowledge after each record (auto)
- **BATCH**: Acknowledge entire batch (auto)

**Why MANUAL**:
- Full control over when to commit offset
- Can skip bad messages (acknowledge without processing)
- Can retry failed messages (don't acknowledge)
- Required for "at least once" with retries

**Error Handler**:
```java
factory.setCommonErrorHandler(new DefaultErrorHandler());
```
- Handles exceptions thrown from listener
- Default: retry 10 times with exponential backoff
- After retries exhausted, message is skipped
- Production: customize with Dead Letter Publishing

## How It Works: Message Flow

### 1. Producer Publishes Event
```java
// In accounts-service
NotificationEvent event = NotificationEvent.builder()
    .eventId(UUID.randomUUID().toString())
    .userId(123L)
    .notificationType(ACCOUNT_CREATED)
    .title("Welcome!")
    .message("Your account is ready.")
    .sourceService("accounts-service")
    .timestamp(System.currentTimeMillis())
    .build();

kafkaTemplate.send("account-created", event.getUserId().toString(), event);
```

### 2. Message in Kafka
- Stored in "account-created" topic
- Partition determined by key (userId)
- Replicated across brokers (RF=3 in prod)
- Retained for 7 days

### 3. Consumer Polls for Messages
- Spring Kafka container polls every 500ms
- Fetches up to 100 records
- Deserializes JSON to NotificationEvent
- Calls @KafkaListener method

### 4. Listener Processes Message
- Validates event
- Checks idempotency (future)
- Creates notification in database
- Acknowledges message

### 5. Offset Committed
- Kafka updates consumer group offset
- Next poll starts from new offset
- If consumer restarts, resumes from last committed offset

### 6. Error Scenario
- If database write fails:
  - Exception thrown
  - No acknowledgment
  - Message remains in Kafka
  - Consumer retries after backoff
  - After 10 retries, DefaultErrorHandler skips message

## "At Least Once" Delivery Guarantee

### How It's Achieved:

**1. Producer Side** (to be implemented):
```yaml
acks: all  # All replicas must acknowledge
retries: 3  # Retry failed sends
enable.idempotence: true  # Prevent duplicates from retries
```

**2. Broker Side** (configured in Helm):
```yaml
min.insync.replicas: 2  # At least 2 replicas must write
replication.factor: 3  # 3 copies of each message
```

**3. Consumer Side** (implemented):
```java
enable-auto-commit: false  # Manual offset control
ack-mode: manual  # Explicit acknowledgment
acknowledgment.acknowledge()  // Only after successful processing
```

### Result:
- Message guaranteed delivered to consumer
- Consumer acknowledges only after database write
- If any failure occurs, message redelivered
- Idempotency prevents duplicate notifications

### Edge Cases:

**Scenario 1**: Database write succeeds, but consumer crashes before ack
- Result: Message redelivered
- Duplicate notification created
- **Mitigation**: Idempotency check using eventId

**Scenario 2**: Network partition during ack
- Result: Kafka might not receive ack
- Message redelivered
- **Mitigation**: Same as Scenario 1

**Scenario 3**: Kafka broker fails
- Result: Consumer reconnects to another broker
- Uncommitted messages redelivered
- **Mitigation**: Idempotency

## Performance Characteristics

### Throughput:
- **Concurrency**: 3 threads × 3 partitions = up to 9 parallel consumers
- **Batch size**: 100 records per poll
- **Estimated**: 1000-5000 notifications/second (depends on database)

### Latency:
- **Network latency**: ~5ms (Kafka within K8s cluster)
- **Deserialization**: ~1ms
- **Database write**: ~10-50ms
- **Total**: ~20-60ms per notification

### Memory:
- **Base**: 100-150MB JVM
- **Buffer**: 100 records × ~1KB = 100KB per poll
- **Total**: ~150MB per instance

### Scalability:
- Horizontal: Add more consumer instances
- Partitions distribute across instances
- Max consumers = number of partitions (3-6)
- Can increase partitions if needed
